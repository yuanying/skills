# ADR に書くもの・書かないもの

## 目的

この文書は、ADR に何を書き、何を書かないかの規約の正典である。
ADR を書く側（`adr-manager` の作成手順）と点検する側（同スキルのレビュー手順、人間のレビュアー）は、
どちらもこの文書だけを基準にする。基準を別の場所に書き足さない。

対象は ADR に固有の規約に限る。第三者が後から読むための書き方の一般論
（一時的なやり取りを残さない、重複を削る、など）は `engineering-writing` スキルに従い、ここには重ねない。

元にした考え方: 「ADR に書くもの・書かないもの」ガイドライン
（https://zenn.dev/tokium_dev/articles/adr-authoring-guideline）。

### 強度

| 強度 | 意味 |
|------|------|
| MUST | 満たさなければならない。満たせないなら ADR を出さず、理由をユーザーに伝える |
| SHOULD | 原則として満たす。外すなら、外す理由を説明できる状態にする（下書きの点検結果やレビューへの返答に書く） |

### 規約の足し方

規約は、ADR のレビューで繰り返された指摘から足していく。最初から網羅しようとしない。

1. 同じ種類の指摘が 2 回以上出たら、規約にする候補とする。
2. A〜G のどのカテゴリに属するかを決める。どれにも当てはまらなければ、カテゴリを足す。
3. そのカテゴリで未使用の次の番号を ID にする。廃止した規約の ID は再利用せず、既存の ID も振り直さない
   （過去のレビュー指摘が ID で参照しているため）。
4. 強度を決め、規約の表に 1 行足す。
5. 「作例」節に OK/NG の作例を足す。例は作例で書き、実在の ADR を引用しない
   （引用元が後で廃止されても例だけが残り、違反した書き方を固定してしまうため）。

規約を廃止するときは、表の行を消さずに強度欄を「廃止」にし、理由を一言添える。

## 規約

### A: 何を参照し、どこに書くか

| ID | 強度 | 規約 |
|----|------|------|
| A-1 | MUST | Context・Decision・Consequences の本文にチケット番号・PR 番号・Issue 番号を書かない。ADR 以外の文書・URL への参照は References 節に集める |
| A-2 | MUST | 関連する ADR と置き換え関係（置き換える／置き換えられる）は Related ADRs 節に書く。本文で他の ADR に触れるときも、Related ADRs に同じ ADR を載せる |

### B: 参照先をどう指すか

| ID | 強度 | 規約 |
|----|------|------|
| B-1 | MUST | コードや文書を物理行番号・章番号だけで指さない。ファイルパスとシンボル名、または節の見出しで指す |
| B-2 | MUST | 他の ADR の決定を指すときは `ADR-NNNN の Decision 項 N（章題）` の形で、番号と章題の両方を書く |

### C: 事実と根拠

| ID | 強度 | 規約 |
|----|------|------|
| C-1 | MUST | 事実として書く内容は、実コード・一次資料と照合してから書き、References に出典と確認日を示す。会議や会話で確認しただけの内容を根拠にしない |
| C-2 | MUST | Context には、このプロジェクトで実際に起きている問題・制約を書く。「〜すると〜になりうる」という仮定の一般論で済ませない |
| C-3 | MUST | ADR 単体で判断を読み取れるようにする。判断に必要な前提・用語は本文で説明し、会話の記録や他の文書を読まないと理由が分からない状態にしない |

### D: 意思決定として書くこと・書かないこと

| ID | 強度 | 規約 |
|----|------|------|
| D-1 | MUST | 移行計画・工程・進捗・タスク表を書かない。移行について決めたことは、移行中に守る条件として書く |
| D-2 | SHOULD | 例外や暫定措置を認めるときは、その失効条件（いつ・何が起きたら終わるか）を書く |
| D-3 | SHOULD | 適用範囲を書き、Decision の末尾の「本 ADR で決定しないこと」に決めなかった事項を挙げる。各事項には委譲先（別の ADR・仕様書・担当チームなど）を名指しし、その委譲先が実在して辿れるようにする |
| D-4 | SHOULD | Decision は実装の自由度を奪わない粒度で書く。判定は下の「D-4 の判定」に従う |
| D-5 | SHOULD | Consequences には、この決定で良くなること・悪くなること・受け入れるトレードオフを書く。良い面だけを並べない |

### E: ADR 同士・一覧との整合

| ID | 強度 | 規約 |
|----|------|------|
| E-1 | MUST | ADR を `Superseded by ADR-NNNN` または `Deprecated` にしたら、同じ変更で、新旧両方の Related ADRs、その ADR を参照している他の ADR、ADR の一覧（README などにあれば）を追従させる |
| E-2 | MUST | 既存の Accepted の ADR と食い違う決定を書くときは、その ADR を置き換えるか、食い違わない範囲を適用範囲（D-3）で示す。食い違ったまま両方を Accepted にしない |

### F: 表記と語彙

| ID | 強度 | 規約 |
|----|------|------|
| F-1 | SHOULD | 陳腐化しやすい情報（最終更新日、「現在」の件数・利用状況、追従して変わるバージョン番号など）を本文に置かない。判断の根拠として必要な数値は、確認日つきで References に出典を書く（C-1） |
| F-2 | SHOULD | 同じ概念には ADR の中で 1 つの用語を使い、既存の ADR の用語に揃える。タイトルは決定の中身を表し、リンクテキストはリンク先の文書名・見出しにする |

### G: Accepted にする前の点検

| ID | 強度 | 規約 |
|----|------|------|
| G-1 | MUST | 未確定の事項（「要確認」「TBD」、選択肢が絞り切れていない点）が残っているうちは Accepted にせず Proposed にする |
| G-2 | MUST | 認証・認可・秘密情報・外部への送信などセキュリティに関わる ADR は、守る対象、許す範囲、設定漏れや失敗のときにどちらへ倒すかを書き揃えてから Accepted にする |

## D-4 の判定

迷ったら次の問いで判定する。

> 決めた実現方式を別の方式に置き換えたとき、ADR の本文を書き換える必要があるか。

書き換えが必要な記述は ADR ではなく、DR（実装上の判断の記録。PR の description などに残す）か仕様書に属する。
ADR に残すのは、方式を置き換えても変わらない方針・制約・判断の理由である。

たとえば次のものは ADR に書かない。

- 検出・判定のアルゴリズム
- テストの方式
- 関数・型・モジュールの構造、メソッド名
- 環境変数名、設定値の形式（区切り文字、正規化の方法など）
- 個別の対象への権限の割り当て

ADR から外したものは、捨てずに次へ移す。

| ADR から外すもの | 移し先 |
|------------------|--------|
| 実装の詳細（構造・名前・形式・アルゴリズム） | 仕様書、コードコメント |
| 実装上の判断とその理由（DR） | PR の description |
| テストの方式 | テストコード、PR の description |
| 個別の対象への権限・設定の割り当て | 設定ファイル、運用手順書 |
| 移行計画・工程・タスクと進捗（D-1） | Issue、プロジェクト管理ツール |
| 決めなかった事項の検討（D-3） | 委譲先の ADR・仕様書・Issue |
| 検討の経緯・会議の記録 | 議事録。判断に効いた却下理由だけを Alternatives Considered に要約する |

## 作例

例はすべて作例であり、実在の ADR ではない。

### A-1

- NG: 「通知の再送は最大 3 回とする（#482 で合意）。詳しくは https://wiki.example.com/notify を参照。」
- OK: 本文は「通知の再送は最大 3 回とする。」とし、References 節に「通知基盤の運用要件（社内 Wiki、2026-10-01 確認）」と URL を置く。

### A-2

- NG: Decision の途中にだけ「この方針は以前の ADR-0004 を置き換える。」と書き、Related ADRs 節が無い。
- OK: Related ADRs に「Supersedes: ADR-0004 通知の再送をクライアント側で行う」と書き、本文で触れるときも同じ ADR を指す。

### B-1

- NG: 「`src/notify/sender.go` の 120 行目の処理を廃止する。」
- OK: 「`src/notify/sender.go` の `retryLater` による再送を廃止する。」

### B-2

- NG: 「ADR-0004 の 2 番目の決定に従う。」
- OK: 「ADR-0004 の Decision 項 2（再送の上限）に従う。」

### C-1

- NG: 「定例で、配信事業者の API は毎秒 100 件まで受け付けると聞いた。」
- OK: 「配信事業者の API は毎秒 100 件を上限とする。」とし、References に「配信事業者 API リファレンス『レート制限』（2026-10-20 確認）」を置く。

### C-2

- NG: 「通知が重複すると、利用者が混乱する可能性がある。」
- OK: 「再送が二重に走り、同じ請求通知が 1 人に 2 通届く事象が 9 月に 3 件起きている。」

### C-3

- NG: 「先日の議論のとおり、B 案を採る。」
- OK: 「再送を送信キュー側で行う案（B 案）を採る。クライアント側で再送すると、端末が落ちたときに再送が失われるためである。」

### D-1

- NG: 「- [x] 新キューを検証環境に入れた / - [ ] 11 月中に本番を切り替える」
- OK: 「切り替えの間は、旧キューと新キューのどちらから届いた通知も重複なく 1 度だけ配信されなければならない。」

### D-2

- NG: 「管理画面からの通知は当面この方針の対象外とする。」
- OK: 「管理画面からの通知は、管理画面が送信キューを使うようになるまで対象外とする。」

### D-3

- NG: 「通知の送信方式を決める。」で終わり、何を決めていないかが分からない。
- OK: 「本 ADR で決定しないこと」に「通知文面の多言語化（通知文面の仕様書で扱う）」「配信事業者の選定（ADR-0009 で扱う）」と、辿れる委譲先つきで挙げる。

### D-4

- NG: 「宛先は環境変数 `NOTIFY_ALLOW` にカンマ区切りで書き、小文字に正規化してから照合する。」
- OK: 「許可した宛先以外へは送らない。許可の設定が無いときは、送らない側に倒す。」

### D-5

- NG: 「送信キューに寄せることで信頼性が上がる。」だけを書く。
- OK: 「再送が失われなくなる一方、送信キューが止まると全通知が止まる。キューの監視を運用に加えることを受け入れる。」

### E-1

- NG: 新しい ADR-0012 だけを足し、置き換えられた ADR-0004 は Accepted のまま、一覧にも新旧の関係が無い。
- OK: 同じ変更で ADR-0004 の Status を `Superseded by ADR-0012` にし、双方の Related ADRs と一覧を直す。

### E-2

- NG: 「通知はすべて同期で送る。」と書くが、Accepted の ADR-0006 は「外部への送信は非同期にする」と決めている。
- OK: ADR-0006 を置き換えるか、「本 ADR は社内向けの通知に限る（ADR-0006 の Decision 項 1（外部への送信）は変えない）」と適用範囲を示す。

### F-1

- NG: 「最終更新: 2026-10-30。現在の利用者は 1,200 人。」
- OK: 本文には判断に効く条件だけを書く（「利用者が 1 万人規模になっても再送の負荷が上限を超えない方式にする」）。数値の根拠が要るなら References に確認日つきで置く。

### F-2

- NG: 同じ ADR の中で「送信キュー」「通知キュー」「配信待ち行列」が混ざる。タイトルが「通知について」。
- OK: 用語を「送信キュー」に揃え、タイトルを「通知の再送を送信キューで行う」にする。

### G-1

- NG: Decision に「再送の上限は 3 回か 5 回（要確認）」とあるまま Status が Accepted。
- OK: 上限が決まるまで Status を Proposed にし、決まってから Accepted にする。

### G-2

- NG: 「外部の宛先へは許可したものだけ送る。」とだけ書き、許可の設定が読めないときの扱いが無いまま Accepted。
- OK: 守る対象（利用者の連絡先）、許す範囲（許可リストにある宛先）、設定が読めないときは送らない側に倒すことを書き揃えてから Accepted にする。
